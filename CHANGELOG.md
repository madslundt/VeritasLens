# Changelog

## 0.16.4 — 2026-06-14
- **Strip markdown link URLs from lens text.** Web-grounded providers (notably OpenAI's `/v1/responses` with `web_search`) sometimes inline `[Tesla blog](https://tesla.com/...)` markdown into the answer body. The HUD renders raw text and has no markdown layer, so the bare URL leaked onto the display alongside the link label. Every lens text field already funnels through `trimTo` in `personas/_utils.ts`, so the fix wraps that single choke point with a new `stripMarkdownLinks` helper that collapses `[label](url)` → `label`. Bare URLs are left alone (translation transcripts may legitimately contain them). Covers fact-check, trivia, ELI5, Meeting Prep, Companion, Devil's Advocate, Key Questions, Logical Fallacy, and Session Summary in one shot.

## 0.16.3 — 2026-06-14
- **Web search now works on every provider, and real provider citations land in the history.** Until 0.16.2 only Gemini, Claude, OpenRouter `:online` and Perplexity `sonar-*` could ground a fact-style lens; OpenAI, Groq, and DeepSeek were stuck in `groundless` and the wearer always saw the trailing `°` glyph on the badge. And even the providers that did ground had their citations discarded — only the model's self-reported `webSourceDomain` (a bare domain echoed back inside the lens JSON) ever reached the HUD. 0.16.3 closes both gaps. The provider-agnostic `resolveProviderGrounding` resolver now returns two new fields the facade dispatches on: `useResponsesApi: true` switches OpenAI's grounded path from Chat Completions to the new `/v1/responses` endpoint with the built-in `{type: 'web_search'}` tool (gated to `gpt-5*` / `gpt-4.1*` / `gpt-4o*` models — wearers who pinned an o1/o3 reasoning model still see `°` so they know to change model); `prefetchSearch: 'perplexity'` borrows the wearer's existing Perplexity API key to call Perplexity's standalone `/search` endpoint before the DeepSeek chat call, injecting the top results as a `[Web search results]` block in the system prompt (mirrors the existing `sttHost` cross-host borrow pattern — no new host in `app.json`, no second key to manage). Groq gains a `modelOverride: 'groq/compound'` branch — its Tavily-backed compound family exposes `executed_tools[].search_results[]` natively. **New side-channel `onCitations` callback** rides on `callLensStream` parallel to the existing `onGroundingMode` callback; every provider client harvests its native citation shape (Gemini's `groundingMetadata.groundingChunks[].web`, Claude's `web_search_tool_result` content blocks, OpenAI's `url_citation` annotations, Perplexity's `search_results[]`, Groq compound's nested `executed_tools[].search_results[]`) into a shared `WebCitation = {domain, url?, title?, snippet?}` array. A new `citations.ts` module hosts the shared `normalizeWebDomain` (lifted from `personas/meetingPrep.ts` so every provider extractor uses the same defensive lowercase + path/query/fragment stripping) plus `buildCitation` and `dedupeCitations` helpers. The lifecycle stashes the array on `HistoryEntry.webCitations` (optional for back-compat with rows persisted before this work); the HUD's history detail page appends a `Sources: bbc.com · reuters.com · …` sub-page (up to 5 domains, integrated into the existing bullet-row pagination so wearers see ● ○ ○ when the entry has multiple body pages + a sources page). **Meeting Prep gets a graceful fallback**: when the model returns `source: "Web"` but forgets `webSourceDomain`, the lifecycle backfills `claims[0].sourceMeta` from the first real provider citation — closing the "model said Web but didn't cite" failure mode that previously left rows reading `From: Web` with no domain. **New OpenAI Responses client** (`openaiResponses.ts`) and **Perplexity Search bolt-on** (`perplexitySearch.ts`) are code-split via dynamic import — wearers who never use those paths don't pay the bundle cost (1.1 KB + 4.8 KB chunks respectively). **Settings UI** flags DeepSeek's borrow dependency explicitly: when the wearer drafts DeepSeek as their provider, the grounding-capability hint reads either "Grounded via your Perplexity key (DeepSeek has no native web search…)" when a Perplexity key is on file or "Add a Perplexity API key to enable web search on DeepSeek" when it isn't. **New tests**: `tests/citations.test.ts` covers the normalizer, URL extractor, citation builder, and dedupe; `tests/perplexitySearch.test.ts` covers the query builder + the /search round-trip with deduped results; `tests/grounding.test.ts` updated for the new resolver branches (OpenAI Responses API gating, Groq compound override, DeepSeek prefetch intent). 487 core tests passing, 187 even-g2 tests passing.

## 0.16.2 — 2026-06-14
- **Meeting Prep can now verify what the other party is saying against current web results, with `Web · domain` attribution.** Until now Meeting Prep answered strictly from the wearer's prepared notes + labeled attachments (the schema's `source` enum was bound to the user's own attachment labels, so Gemini literally couldn't cite anything else). That works for the wearer's own deal but fails the moment the counterparty asserts a publicly verifiable fact the prep doesn't cover — the canonical example is a mortgage renegotiation where the bank claims "the current base rate is 4.8 %" when the public reference rate is in fact something else. A new opt-in checkbox in the Meeting Prep editor — **"Verify public claims with web search"**, persisted independently of the sections blob at `veritaslens.meetingPrepWebGrounding` so existing prep payloads need no migration — turns on web grounding via the existing `LensGrounding = 'web_search'` plumbing. When the toggle is on, `buildMeetingPrepSchema` admits `'Web'` as an additional value on the top-level `source` enum (the `evidence.source` enum stays attachment-only — verbatim attachment excerpts are still reserved for prep text, not paraphrased web facts) and adds a `webSourceDomain: string` property the model fills with the bare source domain (`nationalbanken.dk`, never a full URL). `buildMeetingPrepPrompt` picks up a new rules block + few-shot example C anchoring the priority order: prep is the source of truth for the wearer's own deal; web is for verifying what the counterparty asserts about the public world; when a counterparty claim conflicts with current public reality, flag the conflict in `answer` and set `source: "Web"` — never use `"Web"` for facts only the wearer's prep can know. `parseMeetingPrepResponse` extracts the domain onto a new optional `sourceMeta?: string` field on `MeetingPrepClaim` (generic name so the slot can carry other source metadata in the future without another schema bump), and the SettingsView history detail renders it as `From: Web · nationalbanken.dk`. **Multi-provider via model self-report, not metadata parsing.** Asking the model to echo the source domain inside its JSON works uniformly across all four grounded providers (Gemini's `google_search`, Claude's `web_search_20250305`, OpenRouter `:online`, Perplexity `sonar-*`) without writing four per-provider citation extractors against four different metadata shapes — the model already saw the URLs in the tool-result phase, so echoing one back is routine. Tradeoff is a small hallucination surface; the parser hardens it with `normalizeWebDomain` (strips a leading `https://`, drops path/query/fragment, lowercases, rejects no-dot strings and runaway lengths) so misbehaving model output drops the domain rather than poisoning the claim. **Groundless fallback works automatically.** When the wearer toggles grounding on but the active provider can't supply web search (OpenAI / Groq / DeepSeek), `resolveProviderGrounding` returns `mode: 'groundless'`, the badge picks up the standard trailing `°` glyph and the history entry persists `groundingMode: 'groundless'` — identical to the fact-style lenses' behaviour. The Settings checkbox also surfaces an inline warning to that effect when the drafted provider would be groundless, computed from the same `resolveProviderGrounding` helper the provider-capability hint uses so the two can't drift. **11 new tests in `tests/personas.test.ts`** cover the schema enum shape with grounding off vs on, evidence.source staying attachment-only when grounding is on, the no-attachments + grounding-on case (`Web`-only enum), prompt rule + example C injection only when grounding is on, parser round-trip of `source: "Web"` + `webSourceDomain` → `sourceMeta`, the belt-and-suspenders rejection of `"Web"` as a source when grounding is off, `normalizeWebDomain` stripping `https://` + path, the garbage-input drop list (no dot, control chars, oversized), and the `sourceMeta` omitted-when-attachment-source invariant. 463 core tests passing, 187 even-g2 tests passing.

## 0.16.1 — 2026-06-13
- **Exit menu now lets the wearer pick "with summary" or "without summary" — the stop-time summary chain is no longer all-or-nothing.** Until now the only knob the wearer had over the final summary was the global "Auto summary" Settings toggle, evaluated minutes earlier — there was no in-session way to say "this conversation went nowhere, just close the lens, don't burn a Gemini call summarising it." The Exit row in the active menu changes shape based on `canGenerateFinalSummary()` (auto-summary feature on AND at least one intermediate tick has fired): when a summary CAN be produced, the single `exit` row is now expanded into two consecutive rows — **`Exit - generate summary`** (the existing behaviour, label unchanged) and a new **`Exit - no summary`** that calls `leaveActiveSession({ skipSummary: true })`. When a summary CAN'T be produced (auto-summary off, or no intermediate tick has landed yet), the menu still shows the original single plain `Exit` row — adding a "no summary" alternative when there's nothing to opt out of would just be noise. The new path skips `captureStopTimeInputs()` entirely rather than just skipping the call to `runStopTimeSummaries`, so a multi-MB WAV closure isn't pinned waiting on GC for a chain we'll never run. Forced teardowns (settings-change auto-leave, runtime stop) keep the default `skipSummary: false` so a summary still lands when conditions allow. `EXIT_LABEL_WITHOUT_SUMMARY = 'Exit - no summary'` exported alongside the existing `EXIT_LABEL_WITH_SUMMARY` for symmetry. Two new tests in `tests/hud.test.ts` lock the menu shape — the four-row "single Exit" layout when `exitGeneratesSummary: false` and the five-row split when `exitGeneratesSummary: true`.
- **Companion (and Devil's Advocate) now expose every tidbit in the conversation to swipe-up, not just the latest analysis's.** The HUD's session-wide swipe scroll has always walked across every persisted entry within the current session — Fact Check has worked this way since launch because `splitResultByClaim` in `src/runtime/lifecycle.ts` splits a multi-claim fact-check result into one history entry per claim, so every claim becomes its own session page and a swipe-up at the latest answer's first page hops to the previous question. Companion and Devil's Advocate were the outliers: both returned `[result]` from `splitResultByClaim`, so a 3-tidbit Companion analysis followed by a 2-tidbit one produced 2 bundled entries, the cursor jumped to the new entry, and the wearer perceived "I can only scroll the latest 2 — the first 3 are gone." They were still in `sessionEntries`, just collapsed into one paginated body each, and the indicator stayed `1/2 .. 2/2` (entries) rather than `1/5 .. 5/5` (claims). Both lenses now split per claim at storage time identically to fact-check / trivia / eli5 / logical-fallacy / bias / key-questions, so each Companion tidbit and each Devil's Advocate counterpoint becomes its own scrollable session page. Cross-analysis swipe-up walks every tidbit back to the very first one of the session; the existing session indicator (`X/Y`), cursor-to-first-new-claim jump, swipe-down hide / swipe-up reveal, and bullet-row within-claim pagination all work unchanged because they already operate on `sessionEntries` regardless of which lens populated them. Meeting Prep stays bundled by design — its `answer` + `evidence` + `follow-up` claims are heterogeneous parts of one response and would lose their answer→evidence correspondence if scattered across the scroll. Session Summary, Game, and Translation also stay bundled because each is a single-result analysis by nature. **Latent bug fixed alongside.** `splitForSynthesis` in `src/runtime/hud.ts` (the direct-call path used by tests and menu-replay) had ALREADY been splitting Devil's Advocate per claim — only the lifecycle storage path returned `[result]`. The two functions are documented as mirroring each other (a divergence means tests would pass with a per-claim shape while real-device history would persist a bundled shape, so any UX assumption shaped by tests could regress silently on hardware). Both paths now agree for Companion AND Devil's Advocate. **Tests.** New cases in `tests/hud.test.ts`: a session-wide swipe-scroll test for Companion that builds two analyses (3 then 2 tidbits, all separately persisted entries), asserts the cursor lands on the first tidbit of the second analysis, and walks three `scrollActiveReason(-1)` calls back through every prior tidbit before the fourth returns `'noop'`; plus a new `splitResultByClaim parity` describe block with three cases pinning Companion's per-claim split, Devil's Advocate's per-claim split (which would have failed before this release and prevents the lifecycle/synthesis divergence from creeping back), and the single-claim pass-through for both.
- **Auto mode no longer mis-fires the moment an in-flight analysis resolves.** The v3 1-deep catch-up queue (`pendingFire`) introduced in 0.14 was meant to preserve a "spoke during a long analysis" utterance and drain it the next tick once `isAnalyzing()` flipped false. In real sessions on smart glasses this read as a bug rather than the intended grace: as soon as the spinner cleared on the result the wearer was reading, a stale silence boundary from seconds ago would fire another analysis against audio captured WHILE the wearer was reading the prior answer (typically their own muttered acknowledgement or the next sentence the speaker had already started). The catch-up gate added in 0.16 helped but couldn't fully eliminate the surprise. v0.16.1 drops the catch-up queue entirely and replaces it with a hard freeze: while `isAnalyzing()` is true the watcher resets `voicedMs`, `silenceMs`, `intervalMs`, the `state` machine, AND `lastByteOffset` on every tick — so voice captured during the analysis never credits toward the next arm-up. After the analysis releases, the wearer must produce a fresh `getStartMs()` of voice followed by `getSilenceMs()` of silence before the next auto-fire; the existing Settings sliders ARE the post-analysis cooldown. Removes `pendingFire` from module-state, from start/stop reset paths, from the top-of-tick drain check, and from the silence-trigger branch. The relevance gate's filler-blocklist + per-lens regex logic is unchanged — only the in-flight handling changed. Existing `tests/autoMode.test.ts` cases that asserted the catch-up drain are updated to assert the new freeze semantics (in-flight voice does not contribute to the next arm cycle; the watcher state machine is fully reset by an analyzing tick).

## 0.16.0 — 2026-06-12
- **Auto listen now works in flowing conversations and suppresses irrelevant audio silently.** The existing Auto mode in 0.15 only fired on a speech→silence boundary, which meant lively back-and-forth conversation that never paused below the silence threshold could go ten minutes without a single analysis firing. It also fired indiscriminately on any voiced audio above the RMS floor, so "yeah, mm-hmm, okay, right" back-channel exchanges pushed irrelevant fact-checks onto the HUD. v0.16 adds a second clock-based trigger that bounds the maximum armed window, and a synchronous relevance gate that suppresses the call (no LLM cost, no HUD change) when the recent tagged-transcript tail doesn't contain content the active lens can act on. **Dual trigger in `autoMode.ts`** — alongside the existing silence trigger, an `intervalMs` accumulator now ticks every `TICK_MS` while in the armed state (does not run in idle; tests assert this). When `intervalMs >= autoModeIntervalMs` the watcher fires the same `config.trigger()` callback the silence path uses, so the lifecycle wiring is unchanged. Default 30 s, settings-controlled 15–120 s via a new slider that shares the same width as the existing min-voice / silence sliders. The interval timer resets on **every** fire path — silence trigger, its own fire, AND gate-suppression — so a suppressed call doesn't immediately re-evaluate the gate on the next 200 ms tick. **Relevance gate (`src/runtime/relevanceGate.ts`)** — a pure, synchronous `shouldAnalyze(segments, lensId)` called just before the `trigger()` would run; `false` skips the call silently and resets the state machine. Reads the last 5 transcript segments (`GATE_TAIL_SEGMENTS`) and applies per-lens regex patterns: fact-checker looks for declarative numeric/superlative claims, trivia for question marks and wh-words, key-questions for "should / let's / the plan is", eli5 for ≥2-char acronyms and -tion/-ology/-ization jargon suffixes, logical-fallacy for absolute "always/never/everyone" and if-then patterns, bias-detector for group-blanket framing ("they always", "the left/right", "those people"), devils-advocate for confident hedge-free assertions. **The gate fails open everywhere it can.** Empty tail → pass (preserves `transcriptMode='off'`). Unknown lens id (translation, meeting-prep, companion, session-summary, future lenses) → pass. **Any** non-ASCII letter in the tail → pass — a Danish ø, German ü, French é, Cyrillic, or CJK character routes through pass-through immediately, since the English regex patterns would otherwise systematically suppress non-English wearers. Threw-callback → pass, so a bug in the gate can never silently kill auto-mode. Auto lens uses **only** the filler blocklist (yeah, mm-hmm, okay, right, sure, exactly, totally, huh, hmm, "I see", "got it", thanks, …) so its two-LLM classifier chain dodges back-channel noise but still runs on substantive content; the classifier itself stays unchanged when it runs. **Wearer-speak bypass** — when `wearerSpeakActive` is true (Translate lens's two-way recording mode where the wearer is mid-sentence preparing a reply), the gate is bypassed entirely. Silently dropping a deliberate wearer utterance because surrounding transcript was filler would feel broken, so the gate never gets a vote in that path. **PendingFire interaction** — the v3 1-deep catch-up queue (`pendingFire`) is preserved unchanged, and the gate also applies at drain time so a 30-second-stale catch-up doesn't fire into a transcript tail that's now pure chit-chat. Bounds remain queue-depth 1, no snowball when a stuck in-flight call finally resolves. **Settings UI** — new max-interval slider lives alongside the existing min-voice + trailing-silence sliders inside the Auto mode `<Show>`, all three pinned to `min-width: 10rem` on the value column so the slider tracks visually line up regardless of label length. A contextual italic hint (`"For smarter Auto listen, turn on Transcript mode — it helps the app skip irrelevant moments."`) appears below the sliders only when Auto listen is on AND transcript mode is off; disappears the moment the wearer flips transcript mode on. **No HUD changes** — auto-fire was already silent in 0.15 (no spinner, no affordance flash), and gate-suppression is silent by design too. The wearer can't tell apart "lens decided not to fire" from "transcript was quiet" — both are non-events. **Tests** — 9 new cases in `tests/autoMode.test.ts` (interval idle no-tick, interval fires, interval resets after silence fire, interval resets after own fire, in-flight queueing through pendingFire, gate suppression on silence + interval paths, state reset after suppression, omitted-shouldAnalyze baseline) plus 22 new cases in `tests/relevanceGate.test.ts` (empty/unknown-id/non-Latin fallbacks, per-lens regex coverage, filler blocklist with hyphen-stripping, tail-window sizing). 611 tests passing.

## 0.15.0 — 2026-06-11
- **Conversation-ready lens redesign — every fact-style lens now carries a single short line the wearer can read on the HUD and immediately repeat out loud.** Earlier the wearer got a verdict or a label and had to mentally parse 200–280 chars of reasoning to find something usable in the next sentence. v0.15 adds a dedicated "repeatable line" field on every claim-shaped lens (all optional in the type union so prior history rows still parse without migration). **Fact Check**: new `correction` field, ≤80 chars — surfaces the actual fact when verdict is FALSE (`"Actually ~9.1%, peaked mid-2022."`) or the best-supported alternative when UNVERIFIED. The HUD's `extractQuestion` for fact-check now prefers `correction` over the longer `claim` summary when the verdict is FALSE so the truth lands on the title slot, not the lie. `reason` tightened 240 → 180 chars. **Trivia**: new optional `alt` field, ≤60 chars — common alternative phrasing of the answer (`"Paris"` + alt `"Paris, France"`; `"Einstein"` + alt `"Albert Einstein"`). `description` tightened 180 → 140 chars with the leading half reserved for the most repeatable supporting detail. **Logical Fallacy**: new `callOut` field, ≤80 chars — a tactful, polite sentence the wearer can literally say in the moment (`"Wait, isn't that a false dilemma?"`, `"Hmm, that feels like a straw man of what they said."`) instead of just the bare fallacy name. The HUD's title slot prefers `callOut` over the fallacy noun. `explanation` tightened 200 → 160 chars. **Bias Detector**: new `counterFrame` field, ≤80 chars — the same underlying claim reframed from the opposite tonal/political angle so the wearer can pivot the conversation rather than just call out the framing. The HUD's title slot prefers `counterFrame` over the abstract `direction` label when the verdict is BIASED. `reason` tightened 200 → 160 chars. **ELI5**: schema split into `oneLine` (≤60 chars, the wearer's punchy restatement) + `expanded` (≤220 chars, the richer plain-language version). The legacy single-blob `explanation` field is kept optional and populated back-from-expanded for back-compat with persisted history; the new HUD renderer reads `oneLine` on top with `expanded` below. **Devil's Advocate**: new `pivot` field, ≤80 chars — a conversational lead-in like `"That's fair, though one thing worth considering is —"` so the wearer doesn't have to invent the framing. `rationale` tightened 280 → 200 chars. **Key Questions**: new `priority` enum (`'CRITICAL' | 'IMPORTANT' | 'NICE'`) on each question — sorted CRITICAL-first at parse time, surfaced in the history badge as `Q1!` / `Q1` / `Q1°` respectively so a glance tells the wearer which question is decision-blocking. 23 new tests in `tests/personas-new-fields.test.ts` lock the round-trip semantics for every new field, the legacy-ELI5 fallback path, the priority sort, char-cap enforcement, and the "omitted when empty" behaviour that keeps old history rows clean on reload.
- **Multi-provider grounding — fact-style lenses now use each provider's native web-search capability, not just Gemini.** Until now `grounding: 'google_search'` on the persona definition only fired for Gemini; on Claude, OpenAI, Groq, OpenRouter, DeepSeek, and Perplexity the same fact-check / trivia / devil's-advocate / companion taps silently fell back to training data, which the wearer had no way to know. A new `src/llm/tools.ts` module owns `resolveProviderGrounding(provider, baseUrl, intent, currentModel)` and translates the provider-agnostic intent into whatever each host actually supports: **Gemini** → `tools: [{ google_search: {} }]` (unchanged); **Anthropic Claude** → appends `{ type: 'web_search_20250305', name: 'web_search', max_uses: 3 }` to the `tools` array alongside the existing `emit_lens_result` output tool (Claude is still forced to call the output tool last, but is allowed to call `web_search` first per Anthropic's tool-use semantics, capped at 3 uses per call to bound latency); **OpenRouter** → auto-appends the `:online` model suffix (`openai/gpt-4o` → `openai/gpt-4o:online`) so OpenRouter's online-search backend kicks in without the user having to remember the suffix; **Perplexity** → swaps the chosen model to `sonar-pro` when the user hasn't already picked a `sonar-*` online model (Perplexity's sonar family has web search built into the model itself, no tool needed). The `LensGrounding` type union widens to `'web_search' | 'google_search'` with the old literal kept as an alias so persona records and persisted history that referenced `'google_search'` still parse without a migration. Each provider client (`src/llm/claude.ts`, `src/llm/openai.ts`) gains a `tools?: unknown[]` / `effectiveModel?: string` option; the dispatcher in `src/llm/index.ts` runs the resolver once per `callLensStream` and plumbs the result to whichever client is active. 15 new tests in `tests/grounding.test.ts` lock the per-provider mapping (gemini/claude/openrouter/perplexity grounded; openai/groq/deepseek groundless; suffix and override no-ops when already applied), and `tests/claude-grounding.test.ts` (2 tests) asserts the `web_search_20250305` tool actually lands in the request body when grounding is requested.
- **`GROUNDLESS` HUD indicator for the three hosts that can't ground.** OpenAI Chat Completions, Groq, and DeepSeek have no native chat-side web search (OpenAI's Responses API is out of scope for this release); when the wearer runs a fact-style lens on one of them the call still fires using training data, but the HUD now appends a `°` glyph to the verdict line on fact-check (`- FALSE°`) and bias (`- BIASED°`) so the wearer immediately sees that the answer came from training data alone — distinguishable from a grounded `- FALSE` at a glance without crowding the badge. The decoration is driven by a new `lensGroundingMode` store signal (`'grounded' | 'groundless'`) that the lifecycle sets from a new `onGroundingMode` callback on `callLensStream` the moment the resolver picks a mode, so the badge is consistent between the in-flight `displaying` frame and the history entry persisted seconds later. `HistoryEntry` gains an optional `groundingMode?: GroundingMode` field — only written when the persona declared grounding, so non-grounded lenses don't pollute the persisted blob — and the persisted value flows back into the HUD on history-detail render so groundless rows from earlier sessions stay decorated on relaunch. `migrateEntry` extended to round-trip the new field and the previously-dropped `tags` array (drive-by fix — old history entries were losing tags on each reload), and the missing `'companion'` case in the migrate switch is now wired (drive-by fix; the lens was added in 0.14 but never persisted through the migrator). 6 new tests in `tests/groundless-decoration.test.ts` lock the verdict-line decoration for fact-check + bias, confirm the no-verdict lens shapes (trivia) are untouched, and assert the full pushHistoryEntries → persist → loadHistory → migrate round-trip preserves `groundingMode`.
- **Streaming heading actually renders on the HUD across every lens with a `streamHeading` config.** The infrastructure for character-by-character answer streaming has been in the persona registry since 0.14, but the runAnalysis path never wired the watch keys to `callLensStream` and the HUD never had a partial-render path — `streamHeading` was effectively dead code. v0.15 wires both sides. **HUD side**: new `setLensStreamingHeading(text)` + `clearLensStreamingHeading()` exports in `src/runtime/hud.ts` write partials directly to the reason container via `upgradeText` (single named-container patch, not a full page rebuild — the G2's bridge bandwidth and screen refresh both tolerate 150 ms throttled writes without strobe). Throttle policy: first call fires immediately so the wearer sees something the moment the stream starts; subsequent calls inside the 150 ms window coalesce into a single trailing flush carrying the most recent value; equal-value writes are deduped so a stream that repeats `Paris` → `Paris` doesn't double-render. Pending flushes are cancelled before the final `setLensResult` rebuilds the page so a trailing throttle can't overwrite the final answer with a stale partial. **Lifecycle side**: the runAnalysis path now computes `watchValueKeys` and `onPartialString` from `analysisPersona.streamHeading.field` and stops the spinner / clears the status row on the first partial so the streaming text isn't competing with the `R1/3` dots for attention. The Meeting Prep special-case (whose schema is built dynamically per-tap from the user's prepared sections) switches from `callLens` to `callLensStream` and watches `answer` inline since the dynamic schema can't predeclare `streamHeading` at registry time. **New persona configs**: Fact Check now declares `streamHeading: { field: 'correction', synthesize: → fact-check claim with correction=partial }` — the watcher only fires when the verdict is FALSE (correction is empty on TRUE/UNVERIFIED per schema), so the truth lands on the HUD as it streams. Companion adds `streamHeading: { field: 'headline' }` so each tidbit's punchy hook fills in character-by-character, matching the Trivia / Translate pattern. ELI5 adds `streamHeading: { field: 'oneLine' }` so the simplest restatement appears as it types in. 4 new tests in `tests/lens-streaming-heading.test.ts` lock the throttle behaviour: immediate first write, burst coalescing into one trailing flush carrying the most recent value, dedup on equal value, and cancel-pending-flush.
- **Auto classifier now routes to Companion and disambiguates against fact-check / trivia / devil's-advocate.** The Auto picker introduced in earlier releases had no knowledge of the Companion lens (added in 0.14), so on open conversation about a topic worth knowing more about Auto would silently pick fact-check or trivia and produce a worse experience. Companion is now in `AUTO_LENS_CANDIDATES`, the per-candidate description block names it explicitly (`"companion": The speakers raise a concrete TOPIC and a short tidbit (fact / stat / mini-story / unexpected connection) would enrich the next thing the wearer says.`), and three new disambiguation rules in the prompt resolve the most common collisions (fact-checker over companion when there's a check-worthy claim; trivia over companion when there's a direct question; devil's-advocate over companion when there's a clear one-sided position to push back on; companion otherwise). The classifier `reason` field cap is tightened 80 → 60 chars to trim a few tokens off the mandatory first call.
- **Settings hint exposes per-provider grounding capability.** A second `field-hint` under the Provider dropdown computes `resolveProviderGrounding` on the drafted provider/host/model and renders either `"Grounded: fact-style lenses pull fresh web results before answering."` or `"Groundless: this host has no web search — fact-style lenses run on training data only. The HUD marks groundless answers with a trailing °."` — so the wearer knows what they're picking before they start a session. Hint is reactive on the draft selectors so flipping provider/host updates it in place without saving.
- **Game `reveal` text tightened 340 → 240 chars across quiz-mc / true-false / riddle prompts.** Saves ~100 tokens per question × 10 questions = ~1000 tokens per session on the heaviest lens call, with no loss of pedagogical content — the prompts still require a 2-4 sentence walkthrough with a concrete supporting fact. Reduces game-generation latency by ~1-2 s in practice.

## 0.14.0 — 2026-06-10
